# Как вносить изменения

## Правила
1. `main` защищена по смыслу: прямых коммитов в неё не делаем, кроме исправления, которое согласовано с директором.
2. Каждая задача — отдельная ветка от `main`: `feat/...`, `fix/...`, `docs/...`, `chore/...`.
3. Коммиты небольшие и описательные, одна логическая правка на коммит.
4. Перед слиянием: pull request с описанием, зелёный CI, краткое резюме изменений.
5. Не коммитить секреты. `.env` в `.gitignore`, в репозитории только `.env.example` без значений.
6. Не удалять существующие файлы и историю без согласования.
7. После задачи обновить `PROJECT_STATUS.md`: что сделано, что сломано, следующая задача. Записывать только реально проверенные результаты.

## Локальная проверка перед PR
```bash
npm install                                        # один раз; lockfile будет закоммичен отдельным PR
npm run typecheck
npm run build
npm run prisma:validate --workspace @vot-eto-roll/api
```

## Локальная база данных
```bash
docker compose up -d db                             # PostgreSQL 16 на localhost:5432
cp .env.example .env                                # DATABASE_URL уже совпадает с docker-compose.yml
```
Остановить: `docker compose down`. Данные сохраняются в volume `roll-shushi-pgdata`; для полной очистки `docker compose down -v`.

## Шаблон описания PR
- Что изменено и зачем.
- Какие проверки запускались локально и их результат.
- Что не проверено и почему.
- Связь с пунктом `PROJECT_STATUS.md`.
